PHẦN 0 — TỔNG QUAN DỰ ÁN
================================================================================

0.1. DỰ ÁN GỒM HAI NỬA ĐỘC LẬP NHƯNG LIÊN THÔNG

  1. Browser_Extension/
     Tiện ích mở rộng cho Chrome/Edge (Manifest V3). Cho phép người dùng BÔI ĐEN
     một từ/cụm từ trên bất kỳ trang web nào -> hiện popup tra nghĩa tại chỗ,
     kèm phiên âm (IPA), định nghĩa theo từ loại, từ đồng nghĩa, câu ví dụ.
     Người dùng có thể LƯU từ đó vào app Flashcard.

  2. Flash_Card_App/
     Ứng dụng desktop viết bằng Python + Tkinter (giao diện kiểu Anki): quản lý
     bộ thẻ (Decks), học thẻ (Study), duyệt thẻ (Browse), và lưu tiến độ học.

0.2. ĐIỂM NỐI HAI NỬA ("cầu nối")

  Hai nửa chạy ở hai tiến trình khác nhau (trình duyệt vs. Python). Chúng không
  thể gọi hàm trực tiếp. Vì vậy dự án dùng HAI cơ chế:

  (a) HTTP bridge — app Python tự mở một HTTP server nhỏ ở http://127.0.0.1:5000
      (trong server.py). Extension gọi các endpoint của server này để:
        - lấy danh sách deck
        - tạo deck mới
        - lưu 1 thẻ vào app
        - đọc/ghi TỪ ĐIỂN DÙNG CHUNG (dict.json)
        - nhờ app đưa cửa sổ lên trước

  (b) Custom URL protocol "flashcard://" — cho phép extension MỞ app desktop.
      Windows được đăng ký (một lần, qua install_protocol.py) để khi gặp link
      "flashcard://open" thì chạy Flash_Card_App/run_app.bat -> python main.py.

0.3. TỪ ĐIỂN DÙNG CHUNG (khái niệm xuyên suốt)

  File Browser_Extension/dict.json KHÔNG còn là một từ điển tĩnh nặng ~28MB đi
  kèm extension. Nó nay là "BỘ ĐỆM TRA CỨU TỰ LỚN DẦN" (growing lookup cache):

    - Extension tra theo 3 tầng: dict.json -> cache -> Google Translate API
    - Từ mới dịch qua Google được GHI LẠI vào cả cache lẫn dict.json
    - App đọc chính file này để nạp từ vựng vào deck "Từ điển"

  Nhờ vậy extension và app dùng CHUNG một từ điển thống nhất, và càng dùng càng
  nhiều từ được tra offline (không cần mạng).

0.4. CÔNG NGHỆ SỬ DỤNG

  - Extension: JavaScript thuần, Chrome/Edge Extension Manifest V3
               (service worker + content script + chrome.storage.local)
  - App:       Python 3, Tkinter (GUI), sqlite3 (tiến độ học), json (lưu deck)
  - Bridge:    Python http.server (ThreadingHTTPServer) — CHỈ dùng thư viện chuẩn,
               KHÔNG cần pip install gì thêm
  - API ngoài: Google Translate endpoint không chính thức
               (translate.googleapis.com/translate_a/single)

1.2. NGUYÊN TẮC PHÂN TẦNG

  - data/    : Tầng truy cập dữ liệu thô (đọc/ghi file JSON, SQLite). Không
               chứa logic nghiệp vụ.
  - logic/   : Tầng nghiệp vụ (quản lý deck, quản lý thẻ, tính lịch ôn tập).
  - ui/      : Tầng giao diện (Tkinter). Chỉ gọi xuống logic/, không đụng file.
  - server.py: Tầng tích hợp — cầu nối HTTP. Dùng lại chính logic/ + data/,

  Nguyên tắc: server KHÔNG có vùng lưu trữ riêng. Nó tái sử dụng DeckManager và

  và tiến độ trong data/storage/test.db. Không có "dữ liệu hai nơi".

1.3. LUỒNG DỮ LIỆU CẤP CAO

  Bôi đen từ trên web
      -> content.js gửi LOOKUP cho background.js
      -> background.js tra: dict.json -> cache -> Google
      -> nếu là từ mới: ghi cache + đẩy lên /add_dict (dict.json)
      -> popup hiện kết quả
      -> người dùng bấm "Lưu vào Flashcard"
      -> content.js gửi SAVE_WORD
      -> background.js gọi /save_word
      -> server.py gọi CardManager.add_card -> ghi deck JSON + SQLite
      -> server báo "có thay đổi" -> main.py nạp lại dict vào app + refresh UI

PHẦN 2 — BROWSER EXTENSION (Chrome/Edge MV3)
================================================================================

--------------------------------------------------------------------------------
2.1. manifest.json
--------------------------------------------------------------------------------

Đây là "khai báo" của extension. Nội dung chính:

  "manifest_version": 3          -> chuẩn MV3 (mới nhất)
  "name": "Offline Dictionary"
  "version": "1.1"
  "permissions": ["storage"]     -> cần quyền dùng chrome.storage.local

  "host_permissions":            -> các host mà extension được phép gọi
      "http://127.0.0.1:5000/*"    (cầu nối tới app)
      "http://localhost:5000/*"    (phòng khi app bind localhost)
      "https://translate.googleapis.com/*"  (Google Translate)

  "background": {"service_worker": "background.js"}
      -> background.js chạy như service worker (có thể ngủ khi rảnh)

  "content_scripts": [{ "matches": ["<all_urls>"], "js": ["content.js"] }]
      -> content.js được chèn vào MỌI trang web

  LƯU Ý LỊCH SỬ: Bản trước có "action.default_popup" trỏ tới popup.html trên
  thanh công cụ. Popup đó đã được BỎ (xem Phần 7). Giao diện nay chỉ còn popup
  bôi đen. File manifest.json ở THƯ MỤC GỐC là bản cũ, KHÔNG dùng — manifest
  thật nằm ở Browser_Extension/manifest.json.

--------------------------------------------------------------------------------
2.2. background.js (Service Worker)
--------------------------------------------------------------------------------

background.js là "bộ não" của extension: nó tra từ, gọi Google, gọi app, và
quản lý cache. Content script không tự làm việc này mà gửi message cho nó.

BẢN ĐỒ CÁC HẰNG SỐ & BIẾN TOÀN CỤC
-----------------------------------
  API_BASE = "http://127.0.0.1:5000"   địa chỉ cầu nối (phải khớp server.py)
  CACHE_KEY = "dictCache"              khoá lưu cache trong chrome.storage

  dictionaryData   : bản dict.json giữ trong RAM (null khi chưa nạp)
  dictLoadPromise  : Promise đảm bảo chỉ nạp dict 1 lần
  lookupSeq        : số thứ tự mỗi lần tra, để bỏ kết quả cũ (chống race)

2.2.1. TẦNG 1 — ĐỌC dict.json

  _readPackagedDict()
      Đọc file dict.json ĐÓNG GÓI trong extension bằng
      fetch(chrome.runtime.getURL("dict.json")).
      Đây là bản CHỤP LÚC CÀI — có thể đã cũ so với file trên đĩa.

  _readDictFromApp()
      Gọi GET http://127.0.0.1:5000/dict để lấy dict MỚI NHẤT từ app.
      Trả về object dict, hoặc null nếu app không chạy / trả dữ liệu sai.
      Đây mới là bản app ghi thêm từ vào.

  loadDictionary()
      Chỉ nạp 1 lần (nhờ dictLoadPromise). Thứ tự ưu tiên:
        1) Hỏi app trước (_readDictFromApp) — bản đúng nhất
        2) App không chạy -> dùng bản đóng gói (_readPackagedDict)
      Gán kết quả vào dictionaryData.

  reloadDictionary()
      Buộc nạp lại từ app (xoá cache Promise). Dùng sau khi biết app vừa ghi
      thêm từ, để không đẩy trùng. Trả true nếu lấy được bản mới.

2.2.2. TẦNG 2 — CACHE trong chrome.storage.local

  loadCache()
      Đọc object "dictCache" từ chrome.storage.local. Trả {} nếu chưa có.

  saveToCache(word, entry)
      Đọc cache -> thêm/sửa [word] -> ghi lại toàn bộ vào storage.

  pushToSharedDict(word, entry)
      POST /add_dict với {entries: {word: entry}} để ghi vào dict.json.
      App không chạy -> thất bại êm (catch -> null), cache vẫn giữ từ đó.

2.2.3. BÓC TÁCH DỮ LIỆU TỪ GOOGLE TRANSLATE

  parseTranslateResponse(data)  — HÀM QUAN TRỌNG NHẤT của file
      Nhận mảng JSON thô từ Google và trích ra:
        { ipa, meaning, definitions, synonyms, examples }

      Endpoint translate_a/single trả về MẢNG KHÔNG CÓ NHÃN, vị trí các phần
      phụ thuộc tham số dt=. Với dt=t,rm,bd,md,ex, cấu trúc là:

        data[0]  -> các đoạn dịch; phiên âm nằm ở ô [i][2] hoặc [i][3]
        data[1]  -> từ điển theo từ loại:
                    [pos, [nghĩa tiếng Việt...], [[nghĩa, [từ English nguồn]], ...], ...]
        data[12] -> định nghĩa gốc (Oxford): [pos, [[định nghĩa, id, ví dụ], ...], ...]
        data[13] -> câu ví dụ: [[[câu có <b>từ</b>, null...], ...], ...]

      Các bước xử lý:

      (1) BẢN DỊCH: nối tất cả data[0][i][0] lại thành chuỗi nghĩa.

      (2) PHIÊN ÂM (IPA):
          Thực tế IPA nằm ở index 3 (index 2 gần như luôn null). NHƯNG không
          hard-code index: hàm duyệt ô index 2..3 của mọi phần tử, chọn ô nào
          "trông giống IPA" (khớp regex IPA_HINT chứa các ký tự phiên âm
          /ˈˌəɪʊɛɔæɑʌθðʃʒŋ.../) làm chắc. Cuối cùng bọc trong dấu /.../.

      (3) TỪ ĐỒNG NGHĨA:
          Lấy từ data[1][i][2][j][1] — danh sách "từ tiếng Anh nguồn" góp vào
          một nghĩa. Đây là nguồn đồng nghĩa ĐÁNG TIN và MIỄN PHÍ (nằm ngay
          trong response en->vi vốn đã phải gọi). Bỏ chính từ gốc và từ trùng.
          Ví dụ "happy" -> blissful, beatific, merry, felicitous...

      (4) ĐỊNH NGHĨA: lấy từ data[12] theo từng từ loại; item[0] là định nghĩa,
          item[2] là ví dụ gắn với định nghĩa đó.

      (5) VÍ DỤ: ưu tiên data[13]; nếu vắng thì lấy ví dụ cấp định nghĩa ở (4).

      (6) GỘP NGHĨA: giữ trường `meaning` dạng chuỗi như cũ (tương thích ngược),
          nhưng gắn thêm nhãn từ loại: "- nghĩa (Danh từ)\n- nghĩa (Động từ)".

      Mọi truy cập đều PHÒNG THỦ: kiểm tra Array.isArray, kiểm tra null, vì đây
      là API không chính thức — chỉ số có thể thiếu, phần tử có thể null.

  posLabel(pos)
      Dịch nhãn từ loại tiếng Anh sang tiếng Việt qua bảng POS_VI
      (noun -> "Danh từ", verb -> "Động từ", adjective -> "Tính từ", ...).
      Không có trong bảng thì giữ nguyên.

  stripTags(html)
      Bỏ thẻ HTML (<b>, </b>...) mà Google chèn vào câu ví dụ.

2.2.4. LUỒNG "TRA TỪ" (action: LOOKUP)

  Đây là luồng trung tâm. Khi nhận message LOOKUP:

    const seq = ++lookupSeq;          // đánh dấu lần tra này
    const text = word.toLowerCase().trim();
    const isStale = () => seq !== lookupSeq;

    B1. Tầng 1: nếu dictFile[text] có -> trả {source:"Offline"}.
    B2. Tầng 2: nếu cache[text] có   -> trả {source:"Đã lưu"}.
    B3. Tầng 3: gọi Google:
         url = .../translate_a/single?client=gtx&sl=auto&tl=vi
               &dt=t&dt=rm&dt=bd&dt=md&dt=ex&q=<text>
         - CHỈ 1 REQUEST duy nhất cho tất cả (dịch + IPA + định nghĩa +
           đồng nghĩa + ví dụ) — tiết kiệm và nhanh.
         - Sau khi có response: nếu isStale() thì bỏ (kết quả đã cũ).
         - Nếu Google trả rỗng (parsed.meaning rỗng) -> success:false,
           KHÔNG ghi vào dict (tránh thẻ rác kiểu "meaning: '-'").
         - Nếu là từ/cụm từ ngắn (length <= 25) -> saveToCache + pushToSharedDict.
           Cụm 2-3 từ như "volunteer editors" vẫn là từ vựng hợp lệ -> lưu.
           Chỉ bỏ qua CÂU DÀI (lưu câu vào từ điển là vô nghĩa).
         - sendResponse({source: "Google" hoặc "Google (Câu dài)"}).

    return true;  // giữ kênh mở cho xử lý bất đồng bộ

  CHỐNG RACE (isStale): nếu người dùng bôi đen liên tiếp, response của lần
  TRƯỚC về muộn sẽ bị bỏ — không ghi từ sai vào từ điển.

2.2.5. LUỒNG "LƯU THẺ" & "NHÓM" (GET_GROUPS / SAVE_WORD / CREATE_GROUP)

  Cả 3 đều gọi API cổng 5000 và trả kết quả về cho content script:
    GET  /groups        -> danh sách deck (dùng để đổ vào ô chọn nhóm)
    POST /save_word     -> lưu 1 thẻ (payload gồm cả dữ liệu phong phú)
    POST /create_group  -> tạo deck mới

  Riêng SAVE_WORD kiểm tra kỹ: res.ok && data.success !== false.

2.2.6. LUỒNG "ĐỒNG BỘ TỪ ĐIỂN" (SYNC_DICT)

  Hướng: dict.json -> cache.  Khi app có thể đã được thêm từ ở nơi khác, kéo
  dict.json về cache. CHỈ thêm từ chưa có, không ghi đè cache sẵn có.

2.2.7. LUỒNG "ĐẨY CACHE LÊN dict.json" (FLUSH_CACHE_TO_DICT) — QUAN TRỌNG

  Đây là CHIỀU NGƯỢC của SYNC_DICT, và là mảnh ghép còn thiếu được bổ sung để
  sửa lỗi "dict.json mãi không đổi":

      VẤN ĐỀ: từ mới chỉ được ghi vào dict.json NẾU app ĐANG CHẠY đúng lúc tra
      từ. Nếu app tắt lúc đó, từ chỉ nằm trong chrome.storage.local và TRƯỚC
      ĐÂY KHÔNG BAO GIỜ được đồng bộ trở lại -> dict.json mãi không đổi.

      GIẢI PHÁP: action này nạp lại dict mới nhất từ app (reloadDictionary),
      rồi đẩy mọi từ có trong cache mà CHƯA có trong dict.json lên POST
      /add_dict. Sau khi thành công, cập nhật luôn dictionaryData trong RAM để
      lần sau không đẩy trùng. Chạy khi app vừa khởi động (xem content.js).

2.2.8. NẠP SẴN KHI KHỞI ĐỘNG

  Dòng cuối file: loadDictionary();  — nạp sẵn dict khi service worker thức
  dậy, để lần tra đầu tiên không bị chậm.

--------------------------------------------------------------------------------
2.3. content.js (Content Script + popup bôi đen)
--------------------------------------------------------------------------------

content.js chạy TRONG mỗi trang web. Nhiệm vụ: bắt thao tác bôi đen, hiện popup
tra từ, cho phép lưu thẻ / mở app. Đây là file chứa nhiều logic UX tinh tế.

BẢN ĐỒ BIẾN TOÀN CỤC
--------------------
  popup            : element DOM của popup hiện tại (null nếu không có)
  lastSelection    : { text, rect, stamp } — đoạn bôi đen gần nhất
  selectionStamp   : số tăng mỗi khi selection THỰC SỰ đổi
  selectionCleared : true khi người dùng đã BỎ chọn (bấm ra ngoài)
  lookupSeq        : số thứ tự lần tra (chống race)
  shownStamp       : stamp đã hiển thị lần trước (chống hiện trùng)
  pendingStamp     : stamp lúc mousedown (để so sánh ở mouseup)
  suppressResult   : chặn popup "mọc lại" khi đóng lúc request đang bay
  hasPendingLookup : true khi có 1 request LOOKUP chưa trả về
  fadingPopup      : element đang mờ dần (tránh chồng 2 popup)

2.3.1. BẮT SELECTION — captureSelection()

  Vì sao phải bắt sớm: nếu chỉ đọc window.getSelection() lúc mouseup thì sai ở
  2 tình huống rất thường gặp:
    (1) Bôi đen xong rồi click ra ngoài -> selection đã bị xoá -> đọc rỗng.
    (2) Bôi ngược (phải->trái) hoặc bôi qua thẻ HTML -> thứ tự anchor/focus
        ngược -> đoạn lấy ra thiếu ký tự đầu/cuối (nguồn gốc lỗi "olunteer e").

  Hàm này được gọi ở CẢ "selectionchange" và "mouseup", để luôn có bản mới nhất.
  Logic:
    - Nếu selection rỗng / đã thu gọn -> selectionCleared = true, return.
    - Lấy text và rect (getBoundingClientRect) TRƯỚC khi selection bị đổi.
    - selectionStamp++ (mỗi selection hợp lệ đều tăng stamp, kể cả trùng nội
      dung -> bôi lại đúng từ trước vẫn hiện popup như mong đợi).
    - lastSelection = { text, rect, stamp }; selectionCleared = false.

2.3.2. LUỒNG CHUỘT — TRA TỪ + ĐÓNG POPUP

  Thứ tự sự kiện: mousedown -> (selectionchange) -> mouseup -> click

  mousedown (bắt ở capture phase):
    - Bấm TRONG popup -> bỏ qua (không đóng).
    - Bấm RA NGOÀI -> đóng popup ngay; đặt pendingStamp = lastSelection.stamp
      và suppressResult = true (chặn popup của request đang bay).

  mouseup:
    - Bấm trong popup -> bỏ qua.
    - currentStamp = lastSelection.stamp.
    - BỎ QUA (không tra từ) nếu:
        + selectionCleared (đã bỏ chọn), hoặc
        + currentStamp === 0, hoặc
        + currentStamp === pendingStamp (selection KHÔNG đổi từ lúc mousedown
          -> chỉ là cú click bình thường), hoặc
        + currentStamp === shownStamp (đã hiện popup cho selection này rồi).
    - Nếu là selection MỚI: đặt shownStamp = pendingStamp = currentStamp,
      suppressResult = false, hasPendingLookup = true, seq = ++lookupSeq,
      rồi gửi message LOOKUP. Trong callback:
        + Nếu seq === lookupSeq -> hasPendingLookup = false.
        + Nếu seq !== lookupSeq -> bỏ (có lần bôi đen mới hơn).
        + Nếu suppressResult -> bỏ (người dùng đã đóng trong lúc chờ).
        + Ngược lại, nếu success -> showPopup(...).

  ĐÂY CHÍNH LÀ CHỖ SỬA LỖI "bấm ra ngoài mà popup vẫn hiện lại liên tục": bản
  cũ so sánh bằng CHUỖI RỖNG nên khi trang không xoá selection cũ (bấm chuột
  phải / bấm vùng trống) nó tưởng là bôi đen mới -> hiện lại popup. Nay dùng
  "con dấu" (stamp) so sánh số, chính xác tuyệt đối.

2.3.3. PHÍM ESC

  keydown Escape: chỉ xử lý khi đang có popup HOẶC có request đang bay
  (if (!popup && !hasPendingLookup) return;). Sau đó: đóng popup, đặt
  pendingStamp = shownStamp = lastSelection.stamp, và suppressResult = true.
  Nhờ hasPendingLookup, Esc hoạt động ngay cả khi popup CHƯA hiện (đang chờ API).

2.3.4. HÀM closePopup() VÀ fadingPopup

  closePopup() thu nhỏ + mờ dần popup rồi xoá khỏi DOM sau 300ms. Biến
  fadingPopup giữ element đang mờ, để nếu mở popup mới ngay thì xoá luôn element
  cũ -> không bao giờ chồng 2 lớp.

2.3.5. HIỆN POPUP — showPopup(word, data, rect, response)

  - Cấu trúc nội dung:

3.2.1. class UiBridge

  VẤN ĐỀ: HTTP server chạy ở thread nền. Tkinter KHÔNG thread-safe — nếu thread
  server gọi trực tiếp widget, app sẽ crash hoặc treo ngẫu nhiên.

  GIẢI PHÁP: UiBridge là cầu nối an toàn giữa thread server và main thread.
    - Dùng queue.Queue chứa các callback.
    - root.after(interval, self._poll) định kỳ (mặc định 150ms) lấy callback
      ra và chạy TRÊN MAIN THREAD.
    - post(callback) được thread server gọi để đẩy việc vào queue.

          * Đọc ipa, meaning; đọc definitions (giữ pos + danh sách định nghĩa),
            synonyms, examples — chỉ nhận nếu đúng kiểu dữ liệu.
          * Bỏ qua bản ghi rác: nếu không có ipa VÀ meaning ∈ ("", "-") VÀ không
            có definitions -> skip (Google trả rỗng).
          * answer = "ipa\nmeaning" (hoặc ipa / meaning / "(chưa có nghĩa)").
          * card = {id, question: word, answer, source: "dict"}.
          * Chỉ thêm definitions/synonyms/examples khi có dữ liệu (để file json
            của thẻ nhập tay không bị phình khoá rỗng).
      - added > 0 -> repo.update_deck(deck).
      - Trả (số thẻ mới, tổng số thẻ, tên deck).

      độ học trong test.db không bị mất.

4.1. MỤC ĐÍCH

  Cho phép extension (hoặc bất kỳ trang web nào) MỞ app desktop. Trình duyệt

  install():

      - command = f'"{run_bat}" "%1"'
      - Ghi vào HKEY_CURRENT_USER\Software\Classes\flashcard :
          (default) = "URL:Flashcard App Protocol"
          "URL Protocol" = ""            <-- đánh dấu đây là URL protocol
        và .../flashcard\shell\open\command :
          (default) = command            <-- lệnh chạy khi mở link
      - CHỈ ghi vào HKEY_CURRENT_USER nên KHÔNG cần quyền Administrator.

  uninstall(): xoá lần lượt các key con rồi key gốc (bỏ qua FileNotFoundError).

  main(): chỉ chạy trên win32; --uninstall/-u thì gỡ, ngược lại cài.

4.3. install_protocol.bat

  cd về thư mục script, gọi "python install_protocol.py %*" (hoặc "py ..." nếu
  không có python), rồi pause để người dùng đọc kết quả. Nhấp đúp là cài xong.

4.4. run_app.bat

  cd /d "%~dp0" (về đúng thư mục Flash_Card_App để import hoạt động), rồi:
      where py -> có thì "py main.py", không thì "python main.py".
  Ưu tiên launcher "py" vì ổn định hơn và tránh alias Microsoft Store.

4.5. CÁCH EXTENSION KÍCH HOẠT

  content.js -> openDesktopApp(): tạo thẻ <a href="flashcard://open"> ẩn, click,

PHẦN 6 — CÁC LUỒNG NGHIỆP VỤ CHÍNH
================================================================================

6.1. LUỒNG "BÔI ĐEN TRA TỪ" (online, từ mới)

  1. Người dùng bôi đen từ trên trang.
  2. selectionchange/mouseup -> captureSelection() tăng stamp, lưu lastSelection.
  3. mouseup: stamp mới -> gửi LOOKUP cho background.js.
  4. background.js: dict.json -> cache -> Google (3 tầng).
  5. Google trả về -> parseTranslateResponse -> {ipa, meaning, definitions,
     synonyms, examples}.
  6. Là từ ngắn -> saveToCache + pushToSharedDict (nếu app chạy).
  7. content.js hiện popup, gắn nhãn "Google".

6.2. LUỒNG "TRA LẠI TỪ ĐÃ BIẾT" (offline)

  1..3 như trên.
  4. background.js: tìm thấy trong dict.json -> nhãn "Offline" (không cần mạng).
     Hoặc thấy trong cache -> nhãn "Đã lưu".

6.3. LUỒNG "LƯU THẺ VÀO APP"

  1. Popup hiện form (nhóm + Lưu). Lấy nhóm qua GET_GROUPS.
  2. Người dùng chọn/tạo nhóm, bấm "Lưu vào Flashcard".
  3. content.js gửi SAVE_WORD (kèm definitions/synonyms/examples nếu có).
  4. background.js POST /save_word.
  5. server.py save_word: gộp answer, gom extra, add_card -> ghi deck JSON +
     SQLite; trả kết quả.
  6. server._notify() -> main.py on_external_change -> sync_dict_into_app() +
     refresh_current_view() -> thẻ hiện ra trong app.

6.4. LUỒNG "MỞ APP TỪ EXTENSION"

  1. App chưa chạy -> popup hiện "Mở Flashcard App".
  2. Bấm -> openDesktopApp() mở flashcard://open (đồng bộ trong click).
  3. Windows chạy run_app.bat -> python main.py.
  4. content.js poll GET_GROUPS mỗi 1s (tối đa 12 lần).
  5. App lên -> form lưu hiện ra ngay; flushCacheToDict() đẩy cache vào dict.json.
  6. Nếu app ĐÃ chạy sẵn -> main.py phát hiện qua /ping, chỉ focus cửa sổ cũ.

6.5. LUỒNG "ĐỒNG BỘ TỪ ĐIỂN HAI CHIỀU" (mấu chốt)

  Chiều A (dict.json -> cache): action SYNC_DICT. Kéo từ mới trong dict.json
      vào cache. Chỉ thêm, không ghi đè.

  Chiều B (cache -> dict.json): action FLUSH_CACHE_TO_DICT. Khi app vừa bật,
      đẩy mọi từ trong cache còn thiếu trong dict.json lên /add_dict.

  Vì sao cần cả hai: nếu app TẮT lúc tra từ, từ chỉ nằm trong cache. Chiều B
  đảm bảo từ đó cuối cùng vẫn vào dict.json (khi app bật) và GIỮ NGUYÊN sau khi
  tắt app. Đây chính là lỗi "dict.json mãi không đổi" đã được sửa.

6.6. LUỒNG "HỌC THẺ"

  Mở deck -> StudyView -> Show Answer -> xem nghĩa + định nghĩa/đồng nghĩa/ví dụ
  -> chọn Again/Hard/Good/Easy -> review_card ghi lịch ôn vào SQLite -> thẻ tiếp
  theo. Hết thẻ -> "Session complete!".

7.5. MẤT DỮ LIỆU PHONG PHÚ KHI LƯU THẺ

  Hiện tượng: thẻ lưu từ extension không có định nghĩa/đồng nghĩa/ví dụ dù popup
  đã tra được.
  Nguyên nhân: content.js gửi SAVE_WORD chỉ với {word, ipa, meaning, group_id};
  server.py save_word cũng BỎ QUA 3 trường này.
  Cách sửa: cả 3 tầng — content.js gửi kèm; server.py gom vào `extra`;
  card_manager.add_card(..., extra=None) ghi vào thẻ. Tham số extra tuỳ chọn để
  tương thích ngược.

7.6. dict.json MÃI KHÔNG ĐỔI (LỖI GẦN NHẤT — quan trọng)

  Hiện tượng: tra từ -> nhập vào app -> app chạy và lưu -> tắt app -> dict.json
  vẫn giữ nguyên như cũ, không thay đổi.
  Nguyên nhân (2 lỗi chồng nhau):
    (1) Không có cơ chế "sync sau". pushToSharedDict chỉ ghi dict.json khi app
        ĐANG CHẠY lúc tra từ. Comment nói "khi app bật sẽ sync sau" nhưng thực
        tế KHÔNG có hàm nào làm việc đó. SYNC_DICT chỉ chạy NGƯỢC LẠI.
    (2) loadDictionary() đọc CHỈ file đóng gói (snapshot lúc cài), không đọc file
        app ghi trên đĩa, rồi cache vĩnh viễn.
  Cách sửa:
    - background.js: thêm FLUSH_CACHE_TO_DICT (cache -> dict.json), tách
      _readPackagedDict/_readDictFromApp, loadDictionary ưu tiên GET /dict, thêm
      reloadDictionary.
    - content.js: thêm flushCacheToDict() gọi khi phát hiện app online (3 thời
      điểm) + khi content script nạp.
    - Bỏ gate isSingleWord -> lưu cả cụm từ <= 25 ký tự.
  Kiểm chứng:
    - Python end-to-end (chạy server thật -> /add_dict -> tắt -> đọc đĩa):
      dict.json VẪN GIỮ từ sau khi tắt app -> 7/7 PASS.
    - Mô phỏng luồng (Node): 8/8 PASS.

PHẦN 8 — QUYẾT ĐỊNH THIẾT KẾ & ĐÁNH ĐỔI
================================================================================

8.1. Vì sao dùng HTTP bridge thay vì Native Messaging?
    Native messaging mạnh hơn nhưng phức tạp: phải đăng ký host manifest, cài
    ở registry, khó debug. HTTP cổng 5000 đơn giản, dễ hiểu, đủ cho đồ án, và
    mọi thứ đều thấy được qua log.

8.2. Vì sao dùng custom URL protocol thay vì tự chạy app?
    Trình duyệt chặn chạy file trực tiếp. URL protocol là cơ chế CHÍNH THỐNG để
    mở app desktop từ web, chỉ ghi HKCU nên không cần admin.

8.3. Vì sao chỉ nghe 127.0.0.1?
    An toàn: server chỉ phục vụ máy cục bộ, không lộ ra mạng ngoài.

8.4. Vì sao UiBridge dùng queue + root.after?
    Tkinter không thread-safe. Đây là mẫu chuẩn để marshal công việc từ thread
    khác về main thread.

8.5. Vì sao dict.json KHÔNG ghi đè từ đã có?
    Tránh dữ liệu rác (Google đôi khi trả nghĩa kém) ghi đè nghĩa tốt đã lưu.
    "Ưu tiên dữ liệu cũ" là quy tắc an toàn.

8.6. Vì sao ghi file kiểu atomic?
    dict.json là file dùng chung, nhiều request có thể ghi đồng thời. Ghi ra
    .tmp rồi replace đảm bảo file không bao giờ ở trạng thái nửa vời.

8.7. Vì sao chỉ 1 request tới Google?
    Ban đầu định gọi riêng endpoint đồng nghĩa, nhưng endpoint đó ĐÃ CHẾT. Phát
    hiện ra đồng nghĩa nằm ngay trong response en->vi (data[1][i][2][j][1]) vốn
    đã phải gọi -> vừa chính xác hơn vừa bớt 1 request.

8.8. Vì sao lưu cả cụm từ <= 25 ký tự?
    Cụm 2-3 từ như "volunteer editors" là từ vựng hợp lệ. Chỉ CÂU DÀI mới bị bỏ
    (lưu câu vào từ điển là vô nghĩa).

8.9. Vì sao answer gộp "ipa\nmeaning"?
    Giữ tương thích ngược với mọi màn hình cũ (DeckView/Browse/Study chỉ đọc
    `answer`), đồng thời StudyView có logic tách IPA ra hiển thị riêng.
